# RFC 18: Addon Management and Distribution

Author: (to be filled in)

Status: Draft

Date: 2026-07-17

Scope: The *g.extension* and *g.extension.all* tools, a new `grass.addons`
Python library backing them, a package-based distribution channel for
addons (package format, server index, build pipeline), dependency
declaration and resolution for addons, and a future `grass addons`
command line interface. Complementary changes in the OSGeo/grass-addons
repository (manifests, packaging CI, publish script) are proposed here
but implemented there. The wxGUI extension manager is affected only in a
late phase and only as a consumer of the new library.

Companion document: [RFC 18 Implementation
Plan](RFC18_addon_management_plan.md) breaks this design into ordered,
independently shippable stages with verified code references.

## 1. Motivation

*g.extension* is a single 2965-line script that has accumulated five
structural problems:

1. **Windows is a hardcoded, second-class path.** On Windows,
   *g.extension* downloads precompiled zips from one hardcoded server
   over plain HTTP (`http://wingrass.fsv.cvut.cz/...`,
   `g.extension.py:1603`). The `url` option is ignored entirely: `main()`
   calls the install function with no arguments on `win32`
   (`g.extension.py:2932`), so Windows users cannot install from a fork,
   a branch, a different server, or a local directory -- not even for
   pure Python addons that need no compilation.
2. **Everything is compiled, even when nothing needs compiling.** On
   Linux and macOS, every addon -- C or pure Python -- goes through
   `make` (or CMake) because the HTML, Markdown, and man documentation
   is generated by the build. Installing a ten-line Python script
   therefore requires make, a C compiler, git, and the GRASS development
   files (`include/Make/Module.make`).
3. **No dependency handling.** Addons that need Python packages
   (for example sentinelsat or pandas) install fine and fail at first
   use -- or already during the build, because generating a Python
   addon's documentation imports its modules. Users running GRASS under
   pipenv, uv, conda, or a plain venv get no help mapping an addon's
   needs onto their environment. Dependencies between addons and on
   system tools are equally invisible.
4. **Online queries leak into local operations.** Installing from a
   local directory used to clone the official addons repository; commit
   `740266b459` (PR #7746) fixed the worst of it, but an official
   install still performs up to three separate blobless clones of
   OSGeo/grass-addons in one run (`get_addons_paths` at
   `g.extension.py:2833`, reached from `main()`,
   `filter_multi_addon_addons` at `:1473`, and `update_manual_page` at
   `:2484`), and documentation generation contacts the GitHub commits
   API (`utils/mkdocs.py:215`) even for local source builds.
5. **Duplication and untestability.** The script keeps its state in
   module globals (`options`, `flags`, `TMPDIR`, `PROXIES`), which makes
   most of its ~60 functions untestable in isolation.
   `grass.utils.download` was forked from *g.extension* (its docstrings
   still say "modified copy from g.extension") but *g.extension* never
   switched to it and still carries its own copies. *g.extension.all*
   re-implements downloading again. The wxGUI extension manager shells
   out to *g.extension* and parses its stdout.

The intended outcome is a tested library under the `grass` namespace
that *g.extension* (unchanged interface), *g.extension.all*, a future
`grass addons` subcommand, and the GUI all share; a package channel that
makes installation a checksummed copy on every platform; dependency
declaration, checking, and opt-in installation; and offline-clean local
operations. Legacy channels -- compile from source, the wingrass binary
server, copying local files -- remain supported throughout.

## 2. Current state (verified)

All line references are to the repository at the date of this document;
the implementation plan re-verifies them per stage.

- **Sources.** `resolve_source_code()` (`g.extension.py:2723`) maps the
  `url` option to a source type: `official` and `official_fork` (git,
  via the `GitAdapter` class at `:198`, a blobless sparse checkout of
  OSGeo/grass-addons, branch `grass{major}` with fallback to
  `grass{major-1}`, `get_version_branch` at `:500`), local `dir`, local
  `zip`/tar archives, `remote_zip`/`remote_tar.*` (GitHub, GitLab, and
  Bitbucket URLs rewritten to archive downloads via
  `KNOWN_HOST_SERVICES_INFO` at `:2612`), and a dead `svn` fallback
  (`:1673`, `:2830`) for any unrecognized URL.
- **Network.** Endpoints are contacted from about eight functions:
  `git ls-remote`/`git clone` on OSGeo/grass-addons; the GitHub, GitLab,
  and Bitbucket REST APIs for default-branch discovery
  (`get_default_branch`, `:528`); the metadata files
  `https://grass.osgeo.org/addons/grass{N}/modules.xml` and
  `toolboxes.xml` for listing (`etree_fromurl`, `:570`); the wingrass
  server for Windows binaries (`install_extension_win`, `:1595`); and
  the GitHub commits API from documentation generation
  (`utils/mkdocs.py:215`).
- **Build and install.** `install_extension_std_platforms()` (`:1967`)
  drives `make MODULE_TOPDIR=$GISBASE ...` or, for a CMake-built GRASS,
  `cmake` with the installed addon package
  (`cmake/modules/build_addon.cmake`), then installs into the prefix
  (default `$GRASS_ADDON_BASE`, resolved by `resolve_install_prefix` at
  `:2549`; the `-s` flag targets `$GISBASE`). The prefix layout is
  `bin/`, `scripts/`, `etc/<name>/`, and `docs/{html,mkdocs/source,rest,
  man/man1}` (`check_dirs`, `:2466`).
- **Local registries.** Each install updates three XML files in the
  prefix: `extensions.xml` (`write_xml_extensions`, `:1054`),
  `modules.xml` with a per-task `<libgis revision>` element
  (`write_xml_modules`, `:1008`), and `toolboxes.xml` (`:1116`).
  Consumers besides *g.extension* itself: *g.search.modules* merges the
  addon `modules.xml` into tool search, the GUI reads the prefix layout
  (`gui/wxpython/core/globalvar.py`), and *g.extension.all* compares
  each recorded libgis revision against the running
  `gs.version()["libgis_revision"]` to find addons that need a rebuild
  after a core upgrade (`g.extension.all.py:58`), mapping module names
  back to addon names through the server `modules.xml`
  (`find_addon_name`, `:155`).
- **Server side.** For Linux, the server publishes only metadata
  (`modules.xml`, regenerated daily by
  `grass-addons/utils/addons/grass-addons-publish.sh`), build logs, and
  rendered manuals; sources are compiled client-side. Windows binaries
  are built externally at CTU Prague per addons-repository commit
  (scripts in the `landam/wingrass-maintenance-scripts` repository).
  The core repository's `documentation.yml` workflow already builds all
  addons in GitHub Actions for documentation purposes
  (`.github/workflows/documentation.yml:185`), which demonstrates the
  feasibility of server-side addon builds in CI.
- **GUI.** `gui/wxpython/modules/extensions.py` builds its dialogs from
  `g.extension --interface-description` and runs *g.extension* as a
  subprocess for listing (`:361`, `:549`), installing (`:532`), and
  removing (`:486`, `:509`), parsing textual output.

## 3. Goals and non-goals

Goals:

- One tested, session-optional library (`grass.addons`) with explicit
  state, exceptions instead of process exits, and a progress interface
  usable by CLI tools and the GUI.
- *g.extension* keeps its documented interface exactly; it becomes a
  thin facade. Existing scripts and the GUI keep working unmodified
  through every phase.
- A package channel where installing an addon is: download, verify
  checksum, extract, register -- no compiler, no git, no doc build, on
  every platform. Pre-rendered documentation ships in the package.
- Configurable servers everywhere, including Windows; offline local
  installs that provably perform zero network operations.
- Declared dependencies (Python packages, other addons, system tools),
  always checked and reported, optionally auto-installed into the
  user's active Python environment, with addon-to-addon resolution.
- Legacy channels preserved: compile from git/zip/dir, the wingrass
  binary server, local file copies. Packages are the preferred channel,
  not the only one.

Non-goals:

- Linux or macOS binary packages for compiled addons. The C-library
  compatibility matrix is a packaging-ecosystem problem (conda, distro
  packages) that volunteer infrastructure should not take on. Compiled
  addons on POSIX systems continue to build from source.
- Automatic installation of system (non-Python) dependencies.
- Package signing (the formats reserve fields for it; see open
  questions).
- Replacing or changing the OSGeo/grass-addons contribution workflow.

## 4. The `grass.addons` library

### 4.1 Name and placement

New package `python/grass/addons/`, importable as `grass.addons`. The
community, the repository name (grass-addons), the website section, and
the environment variable family (`GRASS_ADDON_BASE`, `GRASS_ADDON_PATH`)
all already say "addon"; "extension" survives only in the legacy tool
name. Build-system wiring: an entry in `python/grass/Makefile`
(`SUBDIRS`), an entry in the `PYDIRS` list in
`python/grass/CMakeLists.txt`, and a leaf-package `Makefile` modeled on
`python/grass/utils/Makefile`.

### 4.2 Module layout

| Module | Responsibility |
| --- | --- |
| `exceptions.py` | Exception hierarchy under `AddonsError`: `SourceResolutionError`, `FetchError`, `BuildError`, `InstallationError`, `RemovalError`, `RegistryError`, `CatalogError`, `MissingPrerequisiteError`, `OperationCancelled`. The library never calls `gs.fatal()` or prints. |
| `reporter.py` | `Reporter` protocol (`message`, `verbose`, `warning`, `step`, `check_cancelled`) and `NullReporter`. Cancellation is cooperative: the library calls `check_cancelled()` between steps and in long loops; a GUI reporter raises `OperationCancelled`. |
| `config.py` | `AddonsConfig` dataclass replacing today's module globals: an env snapshot, GRASS version and libgis revision, the official repository URL, the catalog (metadata) URL, the Windows binary server URL, the package repository URL, proxies, HTTP headers, make and git program names. `default_config(env=None)` reads `os.environ` exactly once when no env is given. Install prefix resolution moves here. |
| `naming.py` | Pure name helpers (`expand_module_class_name`, `get_module_class_name`). |
| `resolve.py` | `SourceCode` descriptor and source resolution (`resolve_source_code`, known-host rewriting, URL validation, version-branch and default-branch discovery). The `svn` fallback is dropped: an unrecognized URL raises `SourceResolutionError` with a clear message. |
| `fetch.py` | `GitRepository` (the reworked `GitAdapter`): exceptions and reporter instead of `gs.fatal` and verbosity flags, explicit env, and one clone reused for path listing, multi-addon detection, and manual-page fixup within a single operation. `fetch_source()` dispatches archive and directory sources to `grass.utils.download`. Per-request proxy handling replaces the process-global opener. |
| `catalog.py` | Remote metadata access returning data: available addons and toolboxes from `modules.xml`/`toolboxes.xml` (or the package index, later), plus `outdated()` for *g.extension.all*. The dead SVN listing fallback and HTML scraper are dropped. |
| `registry.py` | `LocalRegistry(prefix)`: the three XML writers moved verbatim so `extensions.xml`, `modules.xml`, and `toolboxes.xml` stay byte-compatible, plus readers and install/removal recording. Golden-file tests pin the exact output. Later additive: per-addon receipts (section 6.6). |
| `build.py` | `Builder` protocol (`scan_tool_names`, `build`, `install`, `describe_commands`) with `MakeBuilder` and `CMakeBuilder`; later `PrebuiltPackageBuilder` for the package channel. Subprocess environments are constructed explicitly; the parent process environment is never mutated. |
| `installer.py` | Orchestration of fetch, build, staging, registry update, and manual-page link fixup; prefix layout creation; shebang rewriting. |
| `windows.py` | The precompiled-binary path (today's `install_extension_win`) with the server URL taken from the config. |
| `removal.py` | Removal with a dry-run mode that returns the file list instead of printing it. |
| `operations.py` | The public verbs (below); platform dispatch; prerequisite checks raising `MissingPrerequisiteError` only when the chosen path needs the missing program; per-operation temporary directory lifecycle (a context manager; no `atexit`, no `os.chdir`). |
| `models.py` | Result dataclasses. |
| `manifest.py`, `dependencies.py` | Manifest parsing and dependency handling (sections 5 and 6). |

### 4.3 Public API

```python
install(names, *, url=None, branch=None, fork=False, toolbox=False,
        prefix=None, download_only=False, build_only=False,
        dependencies="check", config=None, env=None, reporter=None)
    -> InstallResult

remove(names, *, force=False, toolbox=False, prefix=None,
       config=None, env=None, reporter=None) -> RemovalResult

list_installed(*, toolboxes=False, prefix=None, config=None, env=None)
    -> list[InstalledAddon]

list_available(*, url=None, branch=None, toolboxes=False,
               config=None, env=None, reporter=None)
    -> list[AvailableAddon]

outdated(*, prefix=None, config=None, env=None) -> list[str]
```

Results are small frozen dataclasses (`InstallResult`, `RemovalResult`,
`InstalledAddon`, `AvailableAddon`, `DependencyReport`) so that the GUI
and the JSON-emitting CLI never parse text. The same five verbs serve
*g.extension*, *g.extension.all*, `grass addons`, and the GUI.

### 4.4 State discipline and sessionless operation

`os.environ` is read once (in `default_config()` when no env is passed)
and never written; today's writes of `GRASS_PREFIX_ADDON_BASE` and
`GRASS_PROXY` move into explicitly constructed child-process
environments. Every `grass.script` call takes `env=`. Each operation
owns a temporary working directory through a context manager that
honors `download_only`/`build_only` by keeping the directory and
returning its path in the result.

Addon management does not touch project or mapset data, so the library
must work without a GRASS session: the install prefix derives from
`get_grass_config_dir_for_version()`
(`python/grass/app/runtime.py:183`) exactly as `resolve_install_prefix`
already does when `GRASS_ADDON_BASE` is unset, and the installation
path from `grass.app.runtime.RuntimePaths`. How to obtain the version
and libgis revision without a session is an open question (section 11)
to settle in the first implementation stage.

### 4.5 Consolidation

`grass.utils.download` stays where it is and becomes the only archive
engine. It gains three backward-compatible extensions: optional request
headers, an explicit extraction directory, and skipping `__pycache__`
entries (the one behavioral delta in *g.extension*'s fork). The
duplicates in *g.extension* (`urlretrieve`/`urlopen` wrappers,
`move_extracted_files`, `extract_zip`, `extract_tar`) are deleted. A
side effect of unifying on the `grass.utils.download` format list is
that xz archives become supported. Dead code is removed: the SVN
download and listing fallbacks and the wxGUI HTML scraper
(`g.extension.py:917`, `:969`, `:1673`).

### 4.6 Facades

*g.extension* keeps its complete parser header and observable behavior;
`main()` becomes a mapping from options and flags to library verbs plus
the existing output formatting, with one
`except AddonsError as e: gs.fatal(...)` at the top level and a
reporter that forwards to `gs.message`/`gs.verbose`/`gs.warning`. Every
current option and flag (`extension`, `operation`, `url`, `prefix`,
`branch`, `proxy`; `-l -c -g -a -s -d -i -f -t -o`) maps one-to-one.
*g.extension.all* switches its detection and name mapping to
`outdated()` and the catalog module but keeps its per-addon subprocess
loop (process isolation per rebuild is a feature). The GUI is untouched
until its own phase; because it shells out to an unchanged
*g.extension*, it doubles as a regression test of facade fidelity.

## 5. Addon packages

### 5.1 Package format

A package is a zip archive of the exact install tree that
`make install` produces today, plus one manifest file at the archive
root:

```text
addon.toml
bin/                      (compiled tools; POSIX or .exe on Windows)
scripts/                  (Python tools)
etc/<name>/               (support files)
docs/html/<tool>.html     (pre-rendered)
docs/mkdocs/source/<tool>.md
docs/man/man1/<tool>.1
```

Installation is: verify checksum, extract, merge into the prefix (the
same file-merging logic today's Windows path uses), record in the
registries. No make, no compiler, no git, on any platform. Packages are
identified by content -- the presence of `addon.toml` at the root -- so
`url=/path/to/file.zip` transparently distinguishes a package from a
source archive.

Naming convention (informative; the manifest inside is authoritative):

```text
{name}-{version}-grass{target}-{platform}.zip

i.sentinel-2.1.0-grass8-noarch.zip
r.example.c-1.4.2-grass8.4.1-windows-x86_64.zip
```

- `name` is the source addon directory name; one package can install
  several tools (the i.sentinel case).
- `version` comes from the manifest; for the long tail of addons with
  no declared version, CI synthesizes `0.<YYYYMMDD>` from the last
  commit date touching the addon directory.
- Pure-Python (`noarch`) packages target a GRASS major version
  (`grass8`), the same compatibility promise as today's source branch.
  Compiled packages target the exact core version they were built
  against (`grass8.4.1`) -- today's per-patch-version wingrass
  directory scheme moved into the artifact.
- Platforms initially: `noarch` and `windows-x86_64`.

Pre-rendered documentation is what removes the build requirement: the
package builder runs inside CI with full git history, so the commit
stamping in `utils/mkdocs.py` uses local git and the GitHub API
fallback is not involved. The API fallback remains only in the legacy
client-side compile channel, gated by the offline switch (section 5.5).

### 5.2 The manifest: `addon.toml`

The manifest lives in two places: committed in the addon source
directory in grass-addons (optional during the transition; CI
synthesizes defaults from the built tools' `--interface-description`
for addons that have none), and copied verbatim into the package root
with a generated `[build]` table appended as text. GRASS requires
Python >= 3.11, so stdlib `tomllib` reads it everywhere; nothing ever
needs to write TOML (all generated artifacts are JSON).

```toml
[addon]
name = "i.sentinel"
version = "2.1.0"
description = "Downloads and imports Copernicus Sentinel products"
keywords = ["imagery", "satellite", "download"]
license = "GPL-2.0-or-later"
authors = ["..."]
tools = ["i.sentinel.download", "i.sentinel.import"]
index_page = "i.sentinel"

[dependencies]
grass = ">=8.4"
python = ["sentinelsat>=1.2", "pandas"]
addons = ["v.example.helper"]
system = [{ name = "gdalwarp", hint = "GDAL command line utilities" }]

[dependencies.optional]
plots = ["matplotlib>=3.5"]

# Appended by CI at package build time:
[build]
date = "2026-07-17T03:12:44Z"
commit = "9f2c1ab..."
platform = "noarch"
grass_target = "8"
grass_version = "8.4.1"
libgis_revision = "8.4.1"
builder = "github-actions/OSGeo/grass-addons"
```

At install time the client copies `[build].libgis_revision` into the
local `modules.xml` `<libgis revision>` element, so the
*g.extension.all* rebuild detection works unchanged for
package-installed addons; "rebuild" for a binary package means
fetching the package built for the new core version.

### 5.3 The index and server contract

One static file per GRASS major version, generated on every publish:

```text
https://grass.osgeo.org/addons/grass8/packages/index.json
```

```json
{
  "format_version": "1.0",
  "generated": "2026-07-17T02:00:00Z",
  "grass_major": 8,
  "addons": {
    "i.sentinel": {
      "description": "...",
      "keywords": ["imagery", "satellite"],
      "tools": ["i.sentinel.download", "i.sentinel.import"],
      "versions": [
        {
          "version": "2.1.0",
          "requires": {"python": ["sentinelsat>=1.2"], "addons": []},
          "packages": [
            {"platform": "noarch", "grass_target": "8",
             "url": "noarch/i.sentinel-2.1.0-grass8-noarch.zip",
             "sha256": "...", "size": 184320}
          ]
        }
      ]
    },
    "r.example.unpackaged": {"description": "...", "versions": []}
  }
}
```

Deliberate properties:

- Package URLs are relative to the index location, so any static
  server, mirror, or fork hosting the same tree shape works without
  rewriting.
- The index lists every addon in the branch, with an empty `versions`
  list when no package exists. Listings are therefore always complete
  regardless of packaging coverage, which makes the index a genuine
  successor to `modules.xml` rather than a partial shadow.
- Dependency summaries (`requires`) are embedded so resolution needs no
  additional requests.
- Every package has a sha256 in the index and a `.sha256` sidecar for
  direct-URL installs. The schema reserves optional signature fields.

`modules.xml` and `toolboxes.xml` continue to be generated unchanged
for as long as any released GRASS parses them; once the index has been
stable for a release cycle they become artifacts derived from it.

### 5.4 Resolution and fallback chain

The package repository base URL is determined by, in order: an explicit
tool option, the environment variable `GRASS_ADDON_REPOSITORY`, and the
default URL above. For `install(name)`:

1. Fetch (or use the cached) `index.json`.
2. Pick the newest version that has either a platform-matching package
   built for the exact running GRASS version, or a `noarch` package for
   the running major version.
3. If found: download over HTTPS, verify sha256, extract, merge,
   register.
4. Otherwise fall back, with a single info-level message, to the legacy
   channel: source compilation on POSIX systems, the wingrass zip on
   Windows.

A user-supplied `url=` bypasses the index and keeps its current source
semantics, except that a zip whose root contains `addon.toml` is
detected and installed as a package.

### 5.5 Configurability, offline behavior, and caching

- `GRASS_ADDON_REPOSITORY` (name following the `GRASS_ADDON_BASE`
  family) selects the package repository; it works on all platforms,
  which gives Windows server choice for the first time.
- `GRASS_ADDON_OFFLINE=1` (and a corresponding option) forbids network
  use: local package and local source-directory installs must succeed
  with zero network operations. The one code change outside the library
  is a conditional in `utils/mkdocs.py` (`get_last_git_commit`,
  `:130`) that skips the GitHub API fallback and uses the existing
  file-date fallback.
- Exactly one file is cached per repository:
  `$GRASS_ADDON_BASE/cache/index-<sha1(base_url)>.json` with its ETag
  or Last-Modified value. Online operations perform a conditional GET;
  offline operations use the cache with a warning stating its date. No
  package caching and no eviction policy.
- The legacy wingrass URL switches from `http://` to `https://`
  (`g.extension.py:1603`) as an immediate, independent fix.

### 5.6 Hosting and build pipeline (changes in OSGeo/grass-addons)

grass.osgeo.org remains the primary and canonical host: the traffic
profile (small zips at addon-install frequency; the server already
serves a 269 KB `modules.xml` to every listing) fits static Apache
hosting, and a plain directory tree is what makes mirrors and the
configurable-server story trivial. GitHub Releases is not built into
the critical path; anyone can host the same tree shape elsewhere.

Proposed pipeline (implemented in OSGeo/grass-addons):

- A new `package-addons.yml` GitHub Actions workflow -- a delta on the
  proven pattern in core's `documentation.yml` (which already builds
  all addons in CI) -- installs GRASS, builds each addon into a
  per-addon scratch prefix, assembles manifest plus tree into a zip,
  and generates `index.json`. The Linux runner ships noarch packages
  only: a build is packaged if and only if its scratch prefix contains
  no compiled objects.
- Windows binary packages are built per core release (not per commit),
  matching the ABI policy, using an OSGeo4W-based build on Windows
  runners. This is the hardest part and is scheduled late; the CTU
  wingrass pipeline is untouched and remains the parallel fallback
  channel indefinitely.
- Publishing is pull-based and atomic: the existing daily
  `grass-addons-publish.sh` cronjob on OSGeo infrastructure downloads
  the latest successful workflow artifact, verifies it, and rsyncs the
  tree, syncing `index.json` last so the index never references a
  missing package. No OSGeo credentials in GitHub secrets.
- `landam/wingrass-maintenance-scripts` is not modified.

## 6. Dependency handling

### 6.1 Declaration

All dependency fields live under `[dependencies]` in `addon.toml`:

- `python`: PEP 508 requirement strings using distribution names (what
  `pip install` takes), for example `"sentinelsat>=1.2"`. Environment
  markers are honored when the `packaging` distribution is importable.
  `[dependencies.optional]` holds named groups that are reported but
  never counted as missing and never auto-installed.
- `addons`: names of required addons, name-only. Addons have no
  independent versioning today (they track a GRASS branch and the
  server publishes one build per addon per major version), so version
  constraints would be unenforceable and would require a real resolver;
  name-only keeps resolution a topological sort. A name satisfied by a
  core tool of the running GRASS (an addon later promoted to core)
  counts as satisfied.
- `system`: informational entries `{name, hint, check}` where `check`
  is `"path"` (verified with `shutil.which`) or `"none"` (only
  printed, for libraries and headers). System dependencies are never
  auto-installed; the field turns cryptic build failures into "you are
  missing GDAL utilities" followed by the hint text.
- `grass`: the minimum core version constraint.

Legacy fallback: when a source has no manifest, a `requirements.txt`
next to the addon's Makefile is parsed leniently (comments and
option lines skipped with a warning) and treated as `python`
requirements. Contributors are asked to migrate the contents into the
manifest; a grass-addons CI check flags addons that have a
`requirements.txt` but no manifest dependency block.

### 6.2 Checking (always on)

The installed-distribution map is built once per check from
`importlib.metadata.distributions()` with PEP 503 name normalization.
Requirement parsing has two tiers: full PEP 508/440 handling when
`packaging` is importable (a soft optional dependency), and a
presence-only fallback otherwise that says explicitly which version
constraints it could not verify. Import probing is rejected:
distribution names are not import names, and imports execute code.

The check runs after fetch and before the build, because building a
Python addon imports its modules for documentation generation --
checking (and optionally installing) first turns a class of today's
build failures into successes. The human-readable summary prints at the
end of the run through `gs.warning` (stderr only; stdout stays
script-parseable), with a copy-pasteable install command tailored to
the detected environment:

```text
WARNING: Addon <r.example> has missing Python dependencies:
  - sentinelsat>=1.2   (not installed)
  - pandas>=2.0        (installed: 1.5.3, does not satisfy >=2.0)
Detected Python environment: virtual environment at /home/user/venv
To install the missing packages, run:
  /home/user/venv/bin/python -m pip install "sentinelsat>=1.2" "pandas>=2.0"
Or re-run with: g.extension extension=r.example dependencies=install
```

Missing dependencies never fail the install by default: they are often
needed by only some code paths, the environment can change after
install, and hard failure would break *g.extension.all* mass rebuilds
the moment metadata appears in grass-addons.

### 6.3 Environment detection

Ordered heuristics; venv-ness is checked first because a venv stacked
on conda or created by uv is operationally a venv:

1. Virtual environment (`sys.prefix != sys.base_prefix`), then
   sub-classified: uv-managed (a `uv = ...` key in `pyvenv.cfg`; uv
   venvs usually have no pip, so the command is
   `uv pip install --python <sys.executable> ...`, falling back to pip
   if uv is absent but pip importable); pipenv (`PIPENV_ACTIVE`; runs
   pip but additionally suggests `pipenv install ...` to record the
   packages in the Pipfile); plain venv
   (`[sys.executable, "-m", "pip", "install", ...]`).
2. Conda (a `conda-meta/` directory in `sys.prefix`): auto-install uses
   pip inside the conda environment -- driving `conda install` is
   rejected because PyPI-to-conda name mapping is unknowable, channel
   choice is user policy, and the solver may mutate unrelated packages.
   The report additionally shows a conda-forge command for users who
   prefer conda hygiene.
3. OSGeo4W on Windows (user-writable, pip-capable): pip via
   `sys.executable`.
4. System Python: if PEP 668 `EXTERNALLY-MANAGED` is present,
   auto-install refuses with an explanation (suggesting the distro
   package or a venv); otherwise `pip install --user`.

Detection returns `PythonEnvironment(kind, prefix, exec_command | None,
suggest_command, notes)`; `exec_command=None` encodes "detected but
refusing to modify".

### 6.4 Opt-in installation and the `dependencies` option

*g.extension* gains exactly one new option:

```text
dependencies=check|install|require|none    (answer: check)
```

- `check` (default): detect, warn, print instructions. The only
  observable change for existing scripts is additional stderr
  warnings.
- `install`: additionally install missing required Python packages into
  the detected environment. The exact command is echoed before running
  and is byte-identical to what `check` printed, so `check` is the dry
  run. Hard safety rules: never sudo, never `--break-system-packages`,
  never an environment whose detection refused. A pip failure warns
  prominently and the addon install proceeds.
- `require`: abort the install with a clear error before any files are
  placed when required dependencies are missing (for CI and
  reproducible setups).
- `none`: no checks and no addon-dependency resolution -- the full
  escape hatch.

Addon-to-addon dependencies are always resolved under `check`,
`install`, and `require`, and only disabled by `none`: installing a
dependency addon stays entirely inside GRASS's own domain (same prefix,
same registry, same uninstaller), whereas Python packages mutate an
environment GRASS does not own, which is why that half is opt-in.

### 6.5 Addon-to-addon resolution

Depth-first traversal over declared `addons` fields; already-satisfied
names (installed per `extensions.xml`, or core tools) are skipped;
a cycle is a hard error printing the cycle path; installation order is
post-order (dependencies first). Python dependencies of the whole
resolved set are aggregated into one report and one pip invocation.
Dependency addons always install from the official index or repository
by name, not from the requester's custom `url=` (documented
limitation; same-source resolution is future work). On removal, reverse
dependencies are computed by scanning the stored manifests of installed
addons; dependents are listed in the existing removal preview, and the
existing `-f` force semantics apply. There is no orphan auto-removal;
the recorded `requested` flag (below) enables it later.

### 6.6 Recorded state

Each install additionally writes `<prefix>/.registry/<addon>/`:

- `manifest.toml` -- verbatim copy of the addon's manifest (for
  legacy installs with only a recovered `requirements.txt`, an
  equivalent `manifest.json` is written instead, since the standard
  library cannot write TOML; readers accept both);
- `install.json` -- installer state: requested-vs-dependency flag,
  source kind and URL, GRASS version, date, and the last dependency
  report.

The three XML registries remain byte-identical in schema and remain
authoritative for legacy readers; the registry directory is purely
additive. A missing `.registry/<addon>/` entry means "installed by an
older *g.extension*, dependencies unknown" and is reported as such.

## 7. Command line interface

### 7.1 *g.extension* (compatibility surface)

The parser interface changes only by the `dependencies` option
(section 6.4). Stdout formats, flags, exit behavior, and the XML
registries are unchanged. *g.extension* remains fully supported
indefinitely as the stable scripting surface.

### 7.2 `grass addons` (later phase)

A new subcommand family following the noun-verb pattern of
`grass project create` and `grass mapset lock`
(`python/grass/app/cli.py:94`, `:193`), added to the launcher dispatch
set at `lib/init/grass.py:2036`:

```text
grass addons install <name>... [--url URL] [--branch BRANCH]
                               [--prefix PATH]
                               [--deps {check,install,require,none}]
grass addons remove <name>...  [--force]
grass addons list              [--format {plain,json}]
grass addons search [PATTERN]  [--format {plain,json}]
grass addons check [<name>...] [--format {plain,json}]
grass addons upgrade [<name>...]
```

It runs without a GRASS session (section 4.4). `check` re-verifies the
recorded dependencies of installed addons against the current Python
environment and exits nonzero when required ones are missing.
`upgrade` is the *g.extension.all* successor. A top-level
`grass install` alias is possible later sugar, not part of this design.
The GUI, in its own phase, switches from subprocess calls to the
library verbs with a `wx.CallAfter`-marshaling reporter, cooperative
cancellation, and a rendered `DependencyReport` (the "install missing
packages" button is disabled, with the explanation shown, when the
environment refuses auto-install).

## 8. Compatibility guarantees

- *g.extension* and *g.extension.all* keep their documented interfaces;
  the only interface addition is the `dependencies` option with a
  behavior-preserving default.
- `extensions.xml`, `modules.xml` (including `<libgis revision>`), and
  `toolboxes.xml` keep their exact schema and formatting, pinned by
  golden-file tests; *g.search.modules*, the GUI, and older GRASS
  versions sharing a prefix are unaffected.
- The server `modules.xml`/`toolboxes.xml` keep being published
  unchanged during the transition.
- The wingrass channel keeps working (over HTTPS) as the Windows
  fallback; the CTU pipeline is not modified.
- Legacy source channels (official git, forks, GitHub/GitLab/Bitbucket
  archives, local zip/tar/dir) remain supported; the removed SVN
  fallback is announced in release notes. An unrecognized plain URL
  resolves to a plain-URL source type which remains usable as a
  metadata location for listing (this is what makes listing from an
  alternative server work), while installing from it produces a clear
  error instead of an attempted `svn checkout`.

## 9. Phasing overview

The implementation is thirteen ordered, independently shippable stages
across two repositories; the companion plan document specifies each.
In outline: extract the library behavior-preservingly (stages 1-4),
make endpoints configurable (5), add manifests and dependency handling
(6-7), stand up the package pipeline and index (8), teach the client
the package channel (9), add Windows binary packages (10), add the
`grass addons` CLI (11), migrate the GUI (12), and make the index the
source of truth (13). The dependency track (6-7), the package track
(8-10), and the CLI/GUI track (11-12) can proceed in parallel once
stage 5 lands.

## 10. Relationship to prior work

Commit `740266b459` (PR #7746) stopped official-repository queries from
leaking into installs from other sources; this RFC completes that
direction: stage 4 guarantees zero network operations for local
installs (asserted by a test) and reduces official installs to a single
clone per operation. `grass.utils.download` -- itself extracted from
*g.extension* years ago -- finally becomes the single archive engine.

## 11. Open questions

- Where the version and libgis revision come from when no session
  exists (`grass.app.resource_paths` constants versus running
  *g.version*); to be settled in stage 1.
- Package signing: the index and sidecar formats reserve fields; a
  minisign/sigstore decision needs a key-management answer for
  volunteer-run infrastructure.
- Per-addon versioning beyond CI-synthesized date versions, which would
  unlock version constraints on addon-to-addon dependencies.
- Whether a top-level `grass install` alias ships alongside
  `grass addons install`.
- The exact name and location of the receipt directory
  (`<prefix>/.registry/` proposed).
